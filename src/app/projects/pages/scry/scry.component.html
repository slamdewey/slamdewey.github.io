Scry
View on GitHub ↗

Scry is a self-hosted viewer for IP cameras — RTSP for the streams, ONVIF for pan/tilt/zoom, anything that speaks both. It's built for a single household: a few cameras, a few devices, watched on the LAN or over whatever VPN you already run. No cloud account, no vendor app, no footage leaving the house.

Architecture

Everything runs on a single Raspberry Pi. A browser on the LAN asks for a page, the request walks down a short stack of services, and — the part worth pausing on — the video itself never walks back up. Media streams directly from the relay to the browser over WebRTC/UDP, bypassing the HTTP layers entirely.

How a stream comes together

The same request that loads the page ends with live video — but it takes a few hops to get there. The browser loads the Angular bundle, the app boots and asks for the camera list, then a click on a camera opens a /stream request that lands at go2rtc, which pulls RTSP from the camera and hands the browser a WebRTC stream:

Decisions I'm happy with

  • Media bypasses the app stack. Proxying video through Node would waste the Pi's headroom, so only the control plane goes through Caddy and scry-server. go2rtc hands WebRTC straight to the browser over UDP — the part that has to be fast doesn't touch the slow path.
  • Cameras are declared, not clicked. A single cameras.yaml is the whole inventory; a per-model models.yaml knows each camera's stream paths and whether it supports PTZ or audio. Adding a camera is IaC.
  • One command to ship. npm run deploy builds the server and web bundles, copies them to the Pi over SSH, regenerates the go2rtc config from those YAMLs, and runs an idempotent install script before restarting the services. No manual steps to forget.
  • It's just a hostname. dnsmasq resolves scry on the LAN, so the whole thing lives at http://s.cry with no IPs to memorize — and it still works over a VPN.
  • Controlled network paths. Nearly all commercially sold IP cameras will channel your streams through their cloud infrastructure before sending to you. There are no encryption standards and these streams are notoriously insecure. This system works entirely within your LAN, which eliminates nearly all conventional attack vectors.

Stack

  • Frontend: Angular — live view, camera list, PTZ overlay.
  • Backend: Node / Express — API plus the reverse proxy to the relay.
  • Streaming: go2rtc — RTSP → WebRTC relay.
  • Edge: Caddy (reverse proxy) and dnsmasq (local DNS).
  • Host: a single Raspberry Pi.

Weird things I ran into

  • Windows won't resolve a dotless hostname. http://scry works fine on phones and most devices, but Windows refuses to resolve single-label names with no dot in them. The fix was petty and perfect: register it as s.cry as well, so http://s.cry resolves everywhere.
  • Mobile Safari has no real fullscreen. iOS Safari's fullscreen video player does not support arbitrary controls. Scry fakes fullscreen on Safari by rendering the stream view sized to the viewport.
  • Most cameras won't stream locally at all. The majority of commercial IP cameras only stream to the manufacturer's cloud first — local access isn't a given. Mine happened to speak RTSP, which go2rtc can pull; other cameras may need a different relay stood up on the Pi. RTSP is also grim security-wise — the password rides in the stream URL in plaintext.
  • Local control APIs are thin. Even cameras that do stream locally expose very little control. Mine gave me pan and tilt over ONVIF but no optical zoom and no night-vision toggle — those live only in the vendor app, which means handing the camera back to their servers. I added digital zoom in the Scry viewer as a consolation prize.
  • Caddy exists so I never type a port. The Node server listens on :8080, but nobody wants to remember that. Caddy sits on :80 and reverse-proxies to it, so a single server plus a single hostname gets you http://s.cry with nothing tacked on the end.
